### What the brief missed

- **Static blast radius of a CardDemo copybook is already public.** An AWS re:Post article walks through the impact of changing `CVACT03Y.cpy` using the AWS Transform dependency JSON. It says "This three-level traversal reveals the full blast radius of a single copybook change", and that 12 programs carry a `Copy` dependency on it (https://repost.aws/articles/ARh6ncZ0kDQlmC03Q7aSZXww/understanding-the-json-dependency-file-from-aws-transform-for-mainframe-assessment). At commit `59cc6c2`, `grep -l "COPY CVACT03Y" app/cbl/*` finds 14 files. A dependency graph alone is therefore a clone. The new part has to be the measurement against execution, and showing the result on the approval step.
- **Hopper's submit card already shows direct impact.** permissions.md, "Approval cards": "Submits show the job name, the source, the steps, the datasets it changes, any Db2 changes, and the JCL." What the card shows is the job's own datasets. It does not show the jobs and outputs downstream of an edited copybook or program.
- **Hopper markets regression checks.** https://www.hypercubic.ai/hopper, "Testing and validation": "Hopper's agent runs the screens and jobs a change touches and checks each result against the last good run, so you know what moved before you promote." No doc page says how "the jobs a change touches" are chosen, or how often that set is right. This is the gap the headline number measures.
- **Hopper's FAQ points to CardDemo as a sandbox.** https://docs.hypercubic.ai/resources/faq.md: "the AWS CardDemo is a public sample application that works well with Hopper." So results on CardDemo are on ground Hypercubic's users already know.
- **Hopper does not handle production change management.** https://docs.hypercubic.ai/ ("What Hopper doesn't do"): "No production change management. Use your existing change tooling for production deploys." The ledger in this build covers the agent's approvals, not production promotion.

**Where the build sits.** Every vendor above has a static graph, and two verify by execution. None publishes how often the static impact set matches what execution shows changed. None puts a transitive impact set, checked against execution, on an agent's approval card. The build measures the first and ships the second. It does not compete with Imogen's rewrite verification or with HyperDocs as documentation.

## 5. Three candidates, scored (BUILD_OUTLINE.md section 2 rubric)

**A. Verified blast radius on the approval step (the brief's build, re-scoped).** A deterministic graph over CardDemo's batch side (COBOL programs, copybooks, JCL steps, DD datasets) predicts which jobs and output datasets a proposed change affects. GnuCOBOL compiles and runs the batch chain before and after the change, and byte-diffs the outputs to give the ground truth. The predicted set is shown on an approval record, alongside an allowlist and a hash-chained ledger with revert.

**B. CardDemo as an agent eval environment.** Graph-generated maintenance tasks ("add a field to CVACT01Y and keep POSTTRAN's output unchanged") with golden-output verifiers, used to score an AI agent such as Hopper's. This is the Polymath reuse target from the brief.

**C. Approval policy proxy only.** An MCP proxy in front of any mainframe agent: allowlist rules, a hash-chained approval ledger and revert. No blast radius.

| Criterion | A | B | C |
|---|---|---|---|
| Their customers feel it | 4: permissions.md tells users to check member names and job classes by eye ("Approve carefully"), and the Hopper page promises "you know what moved before you promote" | 3: users feel agent quality, but no public Hypercubic page asks for an agent benchmark | 3: per-connection modes exist, and the asks for finer rules are inferred from their absence, not from a public request |
| Not a clone | 3: static impact graphs exist at AWS, IBM, Mechanical Orchard and in HyperDocs; the execution-checked accuracy number and the transitive set on the approval card were not found anywhere in table 4 | 4: no published mainframe-agent benchmark found on hypercubic.ai, docs.hypercubic.ai, mechanical-orchard.com or the AWS pages; Imogen's characterization tests are internal to its pipeline | 2: Hopper already has modes, an always-ask list, MCP client levels and a CICS keep-copy restore; "immutable audit trails" is claimed on the home page |
| Tony has proof for it | 4: the method of a graph-driven migration system built at an internship; derm's recorder for the ledger side | 4: derm's eval discipline (E0 baseline, frozen split, five-run bands) | 3: derm's recorder and secret broker; less graph work |
| Fits the budget | 4: the P1 probe passed 11 of 14 batch programs with no LLM, so it runs on ubuntu-latest; the risk is a JCL step runner (section 6) | 2: needs model runs on the box with five-run bands, plus everything A needs to build verifiers | 5: small, no compiler |
| Measurable | 5: precision and recall against GnuCOBOL output diffs, which the graph does not produce | 4: task pass rate against golden outputs; LLM variance needs bands | 2: needs hand-labelled allow and deny decisions, which are a human gate (Tony's labels) |

**Pick: A.** It has the highest total. The SPEC narrows the brief: the graph is a means, not the product, and the headline number is how well the graph's prediction matches execution. The allowlist and ledger stay in scope as the approval record that carries the prediction. B stays a reuse target after P6, because A's harness is most of B's verifier.

## 6. Risks found in P1

| Risk | Evidence | Mitigation (P2 decides) |
|---|---|---|
| Some batch programs do not compile as-is | CBSTM03A, CBEXPORT, CBIMPORT fail the syntax check (`results/P1-feasibility.jsonl`) | Leave them out of the run set and say so, or apply a minimal recorded patch under `fixtures/`. Either way the graph keeps them as nodes. |
| JCL cannot run under GnuCOBOL directly | GnuCOBOL is a compiler. JCL steps (IDCAMS, SORT, IEBGENER) need a runner | A small step runner for the subset the chosen jobs use (EXEC PGM, DD DSN to file, IDCAMS DEFINE and REPRO, SORT FIELDS). The runner is part of the ground-truth side, so P2 freezes it before any graph code exists. |
| Ground truth depends on the input data | An output only changes if the fixture data exercises the changed path | Use CardDemo's shipped ASCII data (`app/data/ASCII/`) unchanged. Report a second table that counts reachable-but-unchanged outputs, so precision loss from the data is visible. |
| A batch utility calls assembler | COBSWAIT CALLs `MVSWAIT` (`app/asm/MVSWAIT.asm`); GnuCOBOL has no assembler | A recorded C or COBOL stub under `fixtures/`, or leave COBSWAIT out of the run set and say so. The graph keeps the CALL edge. |
| CICS programs cannot run | 17 of the 31 programs in `app/cbl` contain `EXEC CICS` | Batch only. CICS programs stay in the graph and are reported as "predicted, not verifiable". |
| AWS's copier count differs from ours | 12 per re:Post, 14 per grep at commit 59cc6c2 | Pin the CardDemo commit. P2 records the exact counts from the pinned tree. |

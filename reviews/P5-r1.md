## Findings

### CB-P5-r1-E1: the release rows say `no GPU` on a machine that has an RTX 3090 (E, minor)

- **Evidence.** Every row in `results/E*.jsonl` and the committed `results/P5-repeat-*.jsonl` has `"machine": "AMD Ryzen 5 9600X 6-Core Processor|121.2 GiB|no GPU"`. On the same machine, `nvidia-smi --query-gpu=name --format=csv,noheader` prints `NVIDIA GeForce RTX 3090`. This review's repeat, run outside srt, wrote `...|121.2 GiB|NVIDIA GeForce RTX 3090`. `approval/evalrun.py:50-60` (`_gpu`) returns `no GPU` whenever `nvidia-smi` fails, and forge DECISIONS.md (P0) records that `nvidia-smi` does not work inside srt. The box avoids this by reading the labels on the host and passing them in as `FORGE_MACHINE_FILE` (forge `sandbox/run-eval.sh` line 28). The P5 session ran `run-eval.sh srt` without setting that variable.
- **Why minor.** No GPU is used, so no score depends on it. The PR and DECISIONS.md both say the label reads `no GPU` because of srt. The label is still wrong as a fact about the machine, and section 6 rule 8 exists so that labels are true.
- **Fix.** Do not edit the rows. Add a note to `results/README.md` saying that `no GPU` in the P5 release rows means the GPU was not visible inside srt, not that the machine had none. For the next run made by hand under srt, write the host's labels to a file and pass it as `FORGE_MACHINE_FILE`, as the box does. A later change to `_gpu` could also return `GPU not visible (nvidia-smi failed)` when the binary exists but fails, and keep `no GPU` for when it is missing. That change goes to the owner of `approval/`.

### CB-P5-r1-D1: the command that made `E1-heldout.jsonl` and `P5-release.json` is not recorded (D, minor)

- **Evidence.** `scripts/p5-eval.py` `release()` writes `P5-release.json` only after all four runs finish, and refuses to start when any release file already has rows. DECISIONS.md (P5) says the first `release` call was killed during E1 heldout and that "E1 heldout was then run once at the same commit". So neither `E1-heldout.jsonl` (run `2026-11-25-27739e5f37d7`) nor `P5-release.json` came from `scripts/eval.sh release`, and no file or PR text names the command that did make them. The row itself is sound: one run, `git_sha` `9a4cd08`, `git_dirty: false`, predictor `graph-dataflow@1`, split hash correct.
- **Why minor.** It is not about a number. Every number has its row, and the release digest matches the head (repeat above).
- **Fix.** Add the exact E1 heldout invocation and how `P5-release.json` was written to the P5 row in DECISIONS.md, or to `results/README.md`. P6 can carry this, because the README must say what ran.

## Not findings

- **Repeat rows in separate files.** eval.md says the runner appends a repeat beside the first run. P5 writes `P5-<tag>-*.jsonl` instead, so that a tracked file is not left dirty. This is logged as an agent's call. The runner's append rule still holds inside each file, and `first_run()` reads the first run of a release file, so a later append cannot change the reference.
- **`rm -rf vendor/carddemo`** in `scripts/eval.sh` runs only when its HEAD is not the pinned commit. `vendor/` is gitignored and is a copy of a pinned public checkout.
- **`forge/eval` failure.** The box lacks the toolchain, and the PR asks Tony to install it (section 2 rule 4, sudo). The review cannot fix that, and it says nothing about the code.
